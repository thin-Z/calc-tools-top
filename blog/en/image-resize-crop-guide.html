Image Resize and Crop: Best Practices for Image Sizing

Preparing an image for a destination is really three separate decisions stacked on top of each other: how many pixels to keep (the ceiling on detail), which part of the frame to keep (composition), and which delivery spec to satisfy (the hard limits set by a platform or a printer). Discuss them as one single "size" and you get the familiar loops: the image still looks soft after following a checklist, or the print shop rejects a file whose DPI was already set to 300. This article separates the three layers, gives numbers you can recompute yourself, and ends with a decision table for e-commerce, social, avatar, and print delivery.

One rule covers everything below: losing pixels is irreversible, changing the aspect ratio costs you content, and DPI is only a label.

1. Three independent problems hiding inside "size"

Size is not one number. It is three layers of information, and getting the order wrong means doing the work twice.

LayerWhat it decidesReversible?Decided by

The working order is ratio first, pixels second, metadata last. Do it backwards and the classic failure appears: you scale the image down to 1920 pixels wide for a screen, then discover the slot is vertical, crop a vertical frame out of a horizontal master, and watch the usable width halve.

2. Cropping is a composition decision, not trimming

The hard part of cropping is never the operation; it is judging whether the subject survives. When one asset has to serve several placements, the binding constraint is the narrowest ratio in the set, not the ratio you happen to have.

Take a 4000 x 3000 photo (about 12 megapixels, 4:3) shot horizontally. To produce a 9:16 vertical cover, the full 3000 pixel height is used, so the maximum width is 3000 x 9 / 16 = 1688 pixels. That is 42% of the original width; the other 58% of the frame has to go. Cropping a vertical frame out of horizontal footage is not a tidy-up, it is a re-shoot of the composition. For precise selections, lock the ratio in the online image cropper rather than typing width and height into a resize form.

  • Keep the subject near the centre: portraits read better with the eyes slightly above centre, and the space below stays available for captions or controls.
  • Stay away from the edges: hold the subject inside roughly the middle 80% of the frame. Platforms re-crop, apply rounded masks, and overlay buttons, and anything touching an edge can be clipped.
  • Shoot once, crop many times: keep the widest original as the master and derive 1:1, 4:3, 16:9, and 9:16 versions from it instead of re-editing one file into every ratio.

3. Choosing a resampling method: one wrong pass cannot be undone

Resizing does not rearrange pixels, it estimates new ones through an interpolation filter. The tool page explains how the filters differ; what matters here is which filter each kind of asset requires, and what goes visibly wrong when you pick the wrong one.

AssetUse thisSymptom when you get it wrongCost
Pixel art, icons, thin lines in screenshotsNearest neighbour, no interpolationHard edges vanish, hairlines turn grey or mushyVisible blockiness when enlarged
Ordinary photographsBicubic or LanczosNearest neighbour introduces colour blocks in skin tones and gradientsSlightly slower

Two facts are worth memorising. Upscaling adds no information: 800 x 600 enlarged to 1600 x 1200 has four times the pixels and exactly the same real detail. Round trips are lossy: detail discarded during a reduction never comes back, so the "shrink it for publishing now, enlarge it later" plan does not work, and the master has to stay at full size. The crop and resize tool uses smooth interpolation when scaling, so you can compare the result against the original and check whether edges have gone soft before exporting.

4. Delivery constraints: ask who receives the file first

There is no universal best size, only constraints handed to you by the receiver. The table below lists decision rules that do not change when a platform redesigns; the exact pixel thresholds do move, so treat each platform's official creator documentation as the source of truth.

Web is the one destination that ignores DPI entirely: browsers read pixels, so DPI metadata is discarded on screen. The familiar advice to use 72 DPI on the web and 300 DPI in print is only true for the print half; what controls sharpness on screen is pixel count and device pixel ratio.

5. DPI is a label, not sharpness

DPI (dots per inch) and PPI (pixels per inch) are used interchangeably in delivery conversations, and both describe how far apart the same pixels are spread in physical space, not how many pixels exist. Two consequences follow:

  • Changing DPI does not change pixels: a 1000 x 1000 file retagged from 72 DPI to 300 DPI still holds one million pixels; only the assumed print size shrinks from about 35.3 cm to about 8.5 cm.
  • Print size = pixels / DPI: run it forwards to size a file for a printer, or backwards to find out how large an existing file can go.

Forwards: A4 is 210 x 297 mm, or 8.27 x 11.69 inches. Then 210 / 25.4 x 300 is about 2480 and 297 / 25.4 x 300 is about 3508, so A4 at 300 DPI needs roughly 2480 x 3508 pixels, about 8.7 megapixels. Adding 3 mm of bleed on all sides takes the sheet to 216 x 303 mm and the requirement to 2551 x 3579 pixels.

Backwards is the more practical direction: how large can the pixels you already have actually print? Using a 4000 x 3000 photo as the example, here is the requirement and the effective resolution side by side.

6. Four worked examples you can recompute

Example 1: 4000 x 3000 down to 800 x 600. The edges shrink to 20%, and the pixel count falls from 12,000,000 to 480,000, which is 4% of the original. Uncompressed RGB data drops from 34.33 MB to 1.37 MB. This is why shrinking first beats adjusting quality alone: the compressor starts with 25 times less raw data.

Example 2: cropping a vertical frame from a horizontal shot. Cropping 4000 x 3000 to 9:16 uses the full 3000 pixel height and leaves 3000 x 9 / 16 = 1688 pixels of width, keeping 42.2% of the pixels. Reverse the order and scale the long edge to 1920 first (giving 1920 x 1440): a 9:16 crop of that file is only 1440 x 9 / 16 = 810 pixels wide, so the best you can deliver is 810 x 1440, short of a typical 1080 x 1920 slot and now needing an upscale. The wrong order throws away a whole generation of resolution.

Example 3: preparing a file for A4 print. A4 at 300 DPI needs 2480 x 3508 pixels, about 8.7 megapixels, rising to 2551 x 3579 with 3 mm of bleed. A common 4000 x 3000 phone photo reaches about 342 DPI across A4, which is enough, but about 6% of the short edge is cropped because 4:3 and A4 do not share a ratio. The same file across A3 drops to about 242 DPI, below the 300 DPI bar, so it suits a large print viewed from a distance or an intentional 200 DPI output.

Example 4: enlarging by two. 800 x 600 enlarged to 1600 x 1200 goes from 480,000 to 1,920,000 pixels, four times as many, while real detail stays identical and the file grows larger. Anything that needs enlarging should be re-exported from the master instead. If the file is still too heavy afterwards, run it through the image compressor once the size is final.

7. FAQ

Will setting DPI to 300 make my image sharper?
No. DPI is a conversion label stored in the file and changing it adds no pixels. A 1000 x 1000 image holds one million pixels whether it is tagged 72 DPI or 300 DPI; only the assumed print size changes, from about 35.3 cm to about 8.5 cm. Real sharpness comes from exporting again from a master with more pixels.
I cropped it exactly as the platform asks, so why is a corner still cut off?
Usually the subject sits too close to an edge and meets a re-crop or a circular mask. Keeping the subject inside roughly the middle 80% of the frame, with a little clearance on every side, avoids it; avatars in particular lose their corners to rounded masks.
What is the difference between cropping first and resizing first?
The difference is how many pixels you still have. Cropping 4000 x 3000 to 9:16 leaves 1688 x 3000, which can be scaled to any target. Scaling the long edge to 1920 first leaves only 810 x 1440 after the vertical crop, forcing an upscale. Crop first, resize second, and the chain resamples only once.
How many pixels does A4 printing really need, and is a phone photo enough?
A4 at 300 DPI needs 2480 x 3508 pixels, about 8.7 megapixels, or 2551 x 3579 with 3 mm of bleed. A typical 4000 x 3000 phone photo is enough: it reaches about 342 DPI across A4. Expect to lose about 6% of the short edge though, since 4:3 and A4 are different ratios.
For several platforms, should I process the image each time or keep one version?
Keep one master sized for the largest requirement and derive the rest from it. The master takes the highest pixel count and widest frame of any delivery, and the derived versions only crop and shrink. Working upwards from the smallest version instead means repeated enlargement and irreversible quality loss.

8. Four common misconceptions

1. Publish the small version now and enlarge it later. Detail lost in a reduction never returns. Keep the master at full size in its original format, save a separate small copy, and keep both.

2. Use resizing where cropping is needed. Forcing a 4:3 image into a 16:9 slot produces a visibly stretched frame. Crop it or pad it, but never stretch it.

3. Assume shrinking is always safe. Reductions depend on the resampling filter too. Nearest neighbour down to 10% turns thin lines in a screenshot into jaggies and moire, while pixel art and icons need nearest neighbour precisely to preserve hard edges.

4. A bigger file means compression failed. When a file grows after resizing, the usual cause is a format change, such as saving a compressed WebP as PNG, or a quality setting that was reset. The trade-offs between formats are covered in the image format guide.

9. Five practical rules

  • Never overwrite the master: keep the full-size, uncompressed, original-format file apart, derive every delivery from it, and let no experiment touch it.
  • Fix the order: crop, then resize, then compress. A fixed order keeps the chain to a single resampling pass and minimises loss.
  • Compose for the narrowest slot: when one asset serves several placements, check the tightest ratio first, usually 9:16 or 1:1, and confirm the subject survives before editing.
  • Batch with consistent specs and names: export at one target size and put the purpose plus dimensions in the filename so versions stay identifiable later.
  • Check the real pixels before delivery: ignore the DPI field in file properties and read the pixel dimensions and ratio instead. Screens read pixels, printers read pixels divided by target size. For further size reduction, see the image compression guide.
